# GitHub Agentic Workflows: A Pets API Test Plan

| [Previous: Copilot CLI][walkthrough-previous] | [Next: Capstone][walkthrough-next] |
|:--------------------------------------------|----------------------------------:|

## Scenario

The shelter wants help identifying gaps in its Flask API tests. Instead of writing
another fixed report script, you'll describe the review in Markdown and let an AI
agent read the API and its tests, compare them, and propose a small test plan.
A volunteer reviews the proposal before changing any code.

This lesson uses **[GitHub Agentic Workflows][about]**, the `gh aw` extension,
and a compiler-generated GitHub Actions workflow. It is not a simulated agent or
an ordinary YAML workflow that directly invokes Copilot CLI.

> [!IMPORTANT]
> The feature is in public preview. This example is compiled with **gh-aw
> v0.88.8**. Reading and compiling it require no model credential or inference.
> **Running it calls real AI**, including a threat-detection pass, and can consume
> Copilot usage and Actions minutes. Staged output prevents issue publication;
> it does not make inference free or deterministic.

## Background

An agentic workflow combines structured configuration with natural-language
instructions. The agent chooses how to analyze the available evidence; the
workflow constrains its access and how its output can affect GitHub.

| Part | This exercise |
| --- | --- |
| Markdown source | `pets-test-plan.md`, with YAML frontmatter and a focused review prompt |
| Compiler output | `pets-test-plan.lock.yml`, an ordinary Actions workflow generated by `gh aw compile` |
| Trigger and approval | Manual dispatch on the default branch, followed by protected `pets-agentic` approval |
| Engine | GitHub Copilot, authenticated separately from repository reads |
| Tools | Read-only GitHub file access in this repository, at most four calls; no agent shell or editor |
| Task | Compare `app/server/app.py` with `app/server/test_app.py` at the run's SHA |
| Safe output | At most one proposed issue, staged for preview rather than published |
| Detection and review | Compiler-provided threat detection, followed by a human checking the proposal against source |

Safe outputs separate the agent's read permissions from jobs that process
structured requests. They don't prove the proposal is correct or replace review.
The file names and 500-word limit are prompt instructions, not filesystem or
token-level access controls. The enforced read boundary is the repository and
allowed GitHub tool. Only use this example with repository content approved for
your selected AI provider.

## 1. Review the source and compiler output

1. Open the [complete Markdown source][source] and its [generated lockfile][lock].
   Keep them in `solutions/` until you deliberately install the lab.
2. Find `on.workflow_dispatch`, the default-branch `if` condition, and
   `on.manual-approval: pets-agentic`.
3. Inspect `permissions.contents: read`, `engine: copilot`, `strict: true`, and
   `network: defaults`. The compiler supplies the firewall and engine access;
   `defaults` does not mean unrestricted network access.
4. Inspect `tools`: `bash`, `edit`, and `cli-proxy` are disabled. The local GitHub
   MCP server exposes only `get_file_contents`, limited to four calls, with an
   approved-integrity policy and a current-repository allowlist. No extra GitHub
   tool PAT is needed for this example.
5. Read the prompt. It asks for evidence at `PETS_REVIEW_SHA`, populated from
   `github.sha`, and tells the agent not to run tests or invent missing coverage.

The safe-output configuration includes:

```yaml
safe-outputs:
  staged: true
  report-failed-jobs: false
  threat-detection:
    max-ai-credits: 50
  create-issue:
    title-prefix: "[Pets test plan] "
    max: 1
    expires: false
```

`staged: true` previews the structured request instead of creating the issue.
Failure-report issue creation is also disabled. `expires: false` avoids adding a
separate issue-maintenance workflow.

Do not assume every generated job has the agent's permissions. Inspect
`activation`, `agent`, `detection`, `safe_outputs`, and `conclusion` individually.
The compiler can retain write scopes in its conclusion/reporting machinery even
with staged outputs. Those scopes are not given to the agent. Review the generated
handlers and staged settings rather than describing the entire workflow as
permissionless. Never add a broad PAT to work around a denied tool or output.

## 2. Compile without running a model

Use the same release as the supplied snapshot. With the GitHub CLI installed and
authenticated for repository access:

```bash
gh extension install github/gh-aw --pin v0.88.8
gh aw version
```

If the extension is already installed, review the version change first, then use
`gh extension install github/gh-aw --pin v0.88.8 --force` to select this release.
The runtime version embedded in the lockfile is compiler-managed and is separate
from the directly installed Copilot CLI in lesson 13.

From your practice repository root, on a feature branch:

```bash
mkdir -p .github/workflows
cp content/github-actions/solutions/14-agentic-workflows/pets-test-plan.md .github/workflows/
gh aw compile pets-test-plan --strict
git status --short
git diff -- .github/workflows/pets-test-plan.lock.yml .github/aw/actions-lock.json
```

The compiler creates `.github/workflows/pets-test-plan.lock.yml` and may create
or update `.github/aw/actions-lock.json`, its action-resolution cache. Read new
untracked files too, since `git diff` alone doesn't show their contents. This
workshop supplies the [reviewed action pins][pins] for reproducibility; in an
existing agentic repository, merge/review pins rather than overwriting its cache.
Fresh resolution may choose newer action releases and produce a different lockfile.
The source opts out of the newer `concurrency.queue` syntax so actionlint v1.7.12
can validate the generated YAML without suppressing errors. Start one demonstration
at a time: ordinary Actions concurrency can replace an older pending run.

Compilation validates the source and may query GitHub or container registries.
It does **not** dispatch Actions, call a model, or create an issue. No `gh aw init`
is required for this self-contained example; that command adds optional authoring
instructions and skills.

Inspect the result before committing. It includes pinned actions, engine/tool
configuration, approval, output processing, and detection. Its internal Node
runtime and artifact handling belong to `gh aw`, not the Flask/Astro build labs.
Do not rewrite the lockfile by hand to make it resemble lesson 10.

> [!NOTE]
> If you only want the credential-free exercise, stop after compilation and the
> [local checks][validation]. You have built and inspected a real workflow, but
> have not executed an agent. Do not present a fabricated report as its output.

## 3. Prepare an owner-authorized run

1. Have an owner enable Actions in the practice repository and confirm eligible
   Copilot access, organization policy, provider data handling, and a usage budget.
2. Create **`pets-agentic`** under **Settings > Environments** before installing
   the workflow. Require an eligible reviewer, prevent self-review, and restrict
   deployment branches to the default branch. Use a public practice repository
   with supported protection rules or an eligible private repository plan.
3. If approval isn't available or there is no independent reviewer, keep this a
   compile-only lab. An environment name alone is not an enforced review gate.
4. For a **personal fork**, follow the [authentication reference][auth] to create
   a short-lived fine-grained PAT with the user-account **Copilot Requests: Read**
   permission. Add it through the GitHub UI as the repository Actions secret
   **`COPILOT_GITHUB_TOKEN`**. Never put it in source, a prompt, or a command line.
   Don't reuse lesson 13's `PETS_COPILOT_TOKEN` name.
5. The environment protects **activation**, not every generated job. A secret
   stored only on `pets-agentic` won't automatically reach the agent and detection
   jobs. This example follows the documented repository-secret setup; keep the
   repository's other workflows and write access trusted.
6. In an eligible **organization-owned** repository, an administrator can instead
   enable centralized Copilot billing and add `copilot-requests: write` to the
   source `permissions`, then recompile. Do not add that permission on a personal
   fork expecting organization billing. This changes who pays and needs explicit
   owner approval.
7. Commit the Markdown source, generated `.lock.yml`, and any reviewed
   `.github/aw/actions-lock.json` changes together. Open a pull request and have
   the owner merge them to the practice repository's default branch. Installing
   only the Markdown is insufficient; Actions executes the lockfile.

If you installed an earlier version of this lesson, disable the old **Pets
agentic simulation** workflow and remove its installed `agentic-safe.yml` through
a reviewed change. It is not part of the `gh aw` exercise.

## 4. Run the actual agent, with staged output

Only continue after authorization for real model usage. Replace `OWNER/REPO` with
your practice repository, and `main` if your default branch has a different name:

```bash
gh aw run pets-test-plan --repo OWNER/REPO --ref main
```

You can also select the workflow in **Actions > Run workflow**. Leave any
compiler-added internal `aw_context` input empty.

1. Observe the activation job waiting for `pets-agentic` approval. Have the
   independent reviewer inspect the run's source commit and approve it.
2. Inspect the agent job: it reads the two files through the permitted tool and
   proposes a test plan. There is no deterministic expected prose.
3. Inspect detection and safe-output processing. The result should be a **staged
   issue preview**, not a new repository issue, commit, or pull request.
4. Verify the proposal's source links, expected HTTP responses, and claims about
   missing assertions. It must acknowledge that it didn't run the tests.
5. If the engine reports missing data, a denied tool, or a budget limit, inspect
   that failure. Don't widen permissions or silently substitute a static report.

Use the run ID from the Actions UI to inspect evidence:

```bash
gh aw logs pets-test-plan --repo OWNER/REPO --count 1
gh aw audit RUN_ID --repo OWNER/REPO
```

Review the tool calls, safe outputs, detection result, token/credit metrics, and
workflow conclusion. Logs and artifacts may contain source and generated content;
apply the repository's retention and access policy, and don't publish raw logs.

### What the limits mean

The main agent has an eight-turn limit, a five-minute agentic-step timeout, and a
100 AI Credit guardrail. Its enclosing job allows 15 minutes for setup and cleanup.
Detection has a separate 50-credit budget and a five-minute job limit. Generated
support jobs have their own compiler defaults.

These are runtime guardrails, **not a dollar guarantee or an account-wide spending
cap**. Actions minutes are separate; cancellations, retries, other workflows, and
provider accounting matter. Re-running a workflow can call AI again. Keep this
manual-only and inspect [cost management][costs] and account budgets before use.

## 5. Change the prompt and recompile

1. On a practice branch, narrow the prompt from at most three proposed cases to
   at most two. Keep its file paths, tools, permissions, and staged mode unchanged.
2. Run `gh aw compile pets-test-plan --strict` again. Review source and lock
   together. The lock metadata records source hashes; some prompt changes may
   alter only metadata rather than visibly replacing generated steps.
3. For a credential-free failure exercise, temporarily change `engine: copilot`
   to `engine: not-an-engine`. Confirm compilation fails, then restore it and
   recompile. Do not push the invalid source or stale lock.
4. A non-default-branch dispatch must skip before agent execution. Review that
   condition locally rather than paying for a run to demonstrate it.

Don't set `staged: false` as part of this lab. Publishing issues is a separate
owner-reviewed behavior change: update permissions/output policy, review the
generated write jobs, and authorize the side effects before running.

After a live demonstration, disable the installed workflow and revoke/remove the
demonstration credential unless an owner has approved continued use.

You've authored a real GitHub Agentic Workflow, compiled its Markdown into Actions
YAML, and separated reading, inference, output processing, and human review.
If you chose the live path, you've also inspected a staged AI-generated test plan
without publishing it or changing the app.
